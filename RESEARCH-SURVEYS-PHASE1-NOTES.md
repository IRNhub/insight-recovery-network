# Research & Surveys — Phase 1 Implementation Notes

**Feature:** UK Family Addiction Impact Survey 2026 + reusable survey framework
**Date:** 20 July 2026

## What was built

### Public survey (insightrecoverynetwork.com)
- Route: `/research/family-addiction-impact-survey-2026`
- Anonymous, no account required, no personal contact information collected.
- Branded split-layout hero (existing `PageHero` component, extended with `primaryAction` + `footnote` props), multi-step form (7 steps: intro/consent → 5 sections → review), progress indicator, back/continue, client-side state persisted in sessionStorage between steps, review screen, double-submit protection via idempotency token, loading/success/error states, closed-survey state.
- `noindex, follow` robots meta (client-side via Helmet AND in prerendered static HTML generated by the new `scripts/prerender-survey.mjs` post-build step). Not present in `sitemap.xml` (survey routes are never added to it). Not linked from any navigation.

### IRNOS admin — "Research & Surveys"
- New tab in the existing admin area (`/admin/research`), alongside Articles / Enquiries / Leads.
- Access uses the existing admin-secret pattern (`x-admin-secret` → `ADMIN_SECRET`). Holders of this secret correspond to Admin / Clinical Director. Therapists, admissions coordinators and finance users do not hold the secret. (Note: the website admin has a single shared secret, not per-user roles — see Limitations.)
- Screens: survey list (status, counts, open/close/archive, copy link), survey dashboard (summary cards, responses by source / country / day), response table (filters: date range, country, relationship, addiction, source, quotation permission, included/excluded, suspected duplicate), individual response view (answers grouped by section, data-quality flags, admin notes), CSV export (valid only or including excluded; respects active filters).

### Database (PostgreSQL + Drizzle, `lib/db/src/schema/surveys.ts`)
Tables: `surveys`, `survey_questions`, `survey_responses`, `survey_answers`, `survey_audit_log`.
- Migration approach follows the project's existing pattern: canonical Drizzle schema + idempotent runtime `CREATE TABLE IF NOT EXISTS` bootstrap (`survey-tables.ts`), same as `resource_leads`. Existing tables and data are untouched. `pnpm --filter @workspace/db run push` remains available for dev.
- Seed (`seed-family-survey.ts`) runs at API server boot, mirrors `seedArticlesIfEmpty`. Idempotent: survey inserted only if the slug is absent; questions upserted by `(surveyId, questionKey)`. Deploying twice never duplicates surveys or questions, and the seed NEVER changes survey status after creation. Created as **Draft** unless `SURVEY_FAMILY_2026_PUBLISH=true` is set on first deploy.
- The framework is generic: question types `single_choice`, `multi_choice`, `scale`, `short_text`, `long_text`, `yes_no`, `consent`. Nothing is hardcoded to the family survey except the seed data and code prefix.

### API
Public (no auth):
- `GET  /api/research/surveys/:slug` — open/closed surveys only (draft/archived → 404); no internal IDs exposed.
- `POST /api/research/surveys/:slug/responses` — submit.

Admin (`x-admin-secret` required, responses served with `X-Robots-Tag: noindex`):
- `GET /api/admin/research/surveys` (+`?archived=true`)
- `GET /api/admin/research/surveys/:id/summary`
- `GET /api/admin/research/surveys/:id/responses` (+filters)
- `GET /api/admin/research/responses/:id`
- `POST /api/admin/research/responses/:id/exclude|restore|notes`
- `POST /api/admin/research/surveys/:id/status` (draft→open, open→closed, closed→open/archived)
- `GET /api/admin/research/surveys/:id/export.csv`
- `GET /api/admin/research/surveys/:id/audit`

## Anonymity & privacy

- No name, email, phone, account ID, client ID, address, postcode, town or clinical-record fields exist anywhere in the survey schema. Extra keys in the submission payload are ignored by validation (tested).
- Responses are identified by a crypto-random code, e.g. `FAM-2026-7K2Q9XWD` (unambiguous alphabet, no personal information).
- Responses are never associated with clients or leads.
- **IP addresses:** raw IPs are NEVER stored. During request processing only, the IP + user agent are combined with a salt (`SURVEY_HASH_SALT` env var; random per-boot value if unset) and hashed with one-way SHA-256 (`clientHash`). This is used solely to flag `suspectedDuplicate` when the same signature resubmits within 12 hours. The hash is excluded from every admin API response, the admin UI, and all exports, and cannot reasonably be reversed. It is never used to identify a participant. Recommendation: set `SURVEY_HASH_SALT` to a long random value in production so duplicate detection survives restarts.
- User agent is reduced to a coarse category (mobile / tablet / desktop / bot) before storage.
- Free-text answers are sanitised server-side (script/HTML stripped, control characters removed, length capped at 4,000 chars).
- Consent (`consentAccepted`) and quotation permission (`quotationPermission`) are separate database fields; submission is rejected server-side unless required consent is `true`.

## Anti-spam / data quality

Honeypot field (`website`, silently discarded), per-client rate limiting (5 submissions / 15 min, matching existing routes), idempotency token with unique constraint (double-submit returns the original success), minimum-realistic-completion flag (<60s → `minimumTimeFlag`), duplicate flag via salted hash, strict server-side validation of every answer against the stored question definitions (client labels/options/status never trusted), max text lengths, sanitisation, failure logging without answer content. No CAPTCHA (per spec — add only if abuse occurs). CSRF: the API is same-origin JSON with restrictive CORS (existing app-level config); no cookies are used for the public survey, so cross-site request forgery has no session to ride.

## Validation (server-side)
Confirms: survey exists; status is Open; required consent true; required questions answered; answer types match question types; options within approved list; scale within range; text within max length; idempotency token unused; rate limit not exceeded.

## Audit log
`survey_audit_log` records: survey opened / closed / archived, response excluded (with reason) / restored, export generated (row count + scope). Actor recorded as `admin` (single-secret auth — no per-user identity available). Answer content is not audited.

## Tests (18 passing — `pnpm --filter @workspace/api-server run test`)
Pure-logic unit tests (no DB required): valid answer sets accepted; required questions enforced; optional text can be blank; invalid options rejected; multi-choice injection/duplication handled; scale bounds; HTML/script sanitisation; length truncation and rejection; personal-contact keys ignored; response-code format and uniqueness; client hash determinism and non-reversibility (no raw IP present); user-agent categorisation; CSV escaping. Full workspace typecheck passes (`pnpm run typecheck`). DB-dependent flows (status transitions, exclusion, export contents) were verified by code review and should be exercised in the deploy environment per the QA checklist below.

## Limitations / assumptions
1. **Roles:** the website admin uses one shared `ADMIN_SECRET`, not per-user roles. "Admin + Clinical Director only" is enforced by secret possession. If the separate IRNOS app later consumes these endpoints, its real role system can gate access; per-user audit actors would need per-user auth.
2. **This admin lives in the website repo**, not the separate IRNOS application (that codebase is external to this repo, which only forwards leads to it via webhook). The API is structured so IRNOS can integrate natively later.
3. **Hero image:** the hero currently uses the site's existing `hero-family-guidance.webp`. To use the supplied campaign image: save it as `artifacts/irn-website/src/assets/family-addiction-impact-survey-2026-hero.webp` (WebP, compressed, ≤ ~250KB) and update the single import at the top of `src/pages/research/FamilyAddictionImpactSurvey.tsx` (a TODO comment marks the spot).
4. Excel (.xlsx) export not included — CSV covers the requirement; the stack has no existing xlsx dependency.
5. In-memory rate limiting resets on restart (matches existing routes; acceptable at current traffic).
6. The results/aggregate public page is out of scope (Phase 2), as is a visual survey builder.
7. GDPR: this implementation collects no personal contact data and stores no raw IPs, but no legal review has been performed; the public page describes actual data handling without compliance claims.

## Opening the survey (launch steps)
1. Deploy this branch (after PR review/merge). The survey seeds itself as **Draft**.
2. Log in at `https://www.insightrecoverynetwork.com/admin` with the admin password.
3. Open the **Research & Surveys** tab → "UK Family Addiction Impact Survey 2026" → **Open survey**.
4. (Recommended) Set `SURVEY_HASH_SALT` env var to a long random string before launch.
5. Share the link with UTM parameters, e.g.:
   - `https://www.insightrecoverynetwork.com/research/family-addiction-impact-survey-2026?utm_source=facebook&utm_medium=social&utm_campaign=family_survey_2026`
   - `.../family-addiction-impact-survey-2026?utm_source=newsletter&utm_medium=email&utm_campaign=family_survey_2026`
   - `.../family-addiction-impact-survey-2026?utm_source=linkedin&utm_medium=social&utm_campaign=family_survey_2026`
6. To stop collection: **Close survey** (page stays up, shows closed message, rejects submissions).
